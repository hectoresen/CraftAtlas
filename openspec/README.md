# CraftAtlas — mandatory OpenSpec / SDD workflow

**Specification truth:** synchronized accepted requirements live in `openspec/specs/`, while historical and proposed delta changes remain in `openspec/changes/<kebab-case-id>/`. **Current implemented feature status is documented in `README.md` and backed by code**; consult `docs/OPENSPEC_STATUS.md` for which historical requirements are still open or superseded. Do not treat an unsynchronized or unverified requirement as a shipped feature. This project uses the `spec-driven` schema from `openspec/config.yaml`. It is not acceptable to implement a behavioral change first and write specs later.

## Install and initialize (terminal)

Current official OpenSpec npm CLI requires Node.js **22.12+**.

```bash
npm install -g @fission-ai/openspec@latest
openspec init     # choose OpenCode; preserve existing openspec/config.yaml
openspec list
```

Initialization generates OpenCode-compatible agent skills/commands locally; these may be regenerated when OpenSpec updates. Do not hand-maintain generated commands. Consult official CLI help if an installed version uses different options.

## Commands (inside the OpenCode chat)

| Core command | Purpose |
| --- | --- |
| `/opsx:explore` | Optional exploration without implementing |
| `/opsx:propose add-material-profession-tooltips` | Produce proposal, delta specs, design and tasks |
| `/opsx:update` | Incorporate review feedback in artifacts |
| `/opsx:apply` | Implement the **approved** proposal and tasks |
| `/opsx:sync` | Synchronize accepted delta specs with canonical specs |
| `/opsx:archive` | Archive after change acceptance |

Expanded optional profile enables `/opsx:new`, `/opsx:continue`, `/opsx:ff`, `/opsx:verify`, `/opsx:bulk-archive` and `/opsx:onboard`: run `openspec config profile` and `openspec update`. **Verification remains mandatory even if `/opsx:verify` is unavailable in the core profile.** Commands may have alternative names in other coding tools; use names generated by `openspec init`.

## Mandatory sequence and approval gates

1. **DISCOVER**: read `AGENTS.md`, existing specs, active changes, repository state and target milestone.
2. **PROPOSE**: `/opsx:propose <short-kebab-case-change>`, creating a problem statement, in/out scope, SHALL requirements with WHEN/THEN scenarios, design and a verifiable task checklist.
3. **STOP FOR HUMAN APPROVAL**: show proposal, risks, architectural changes, data licenses and testing plan to **@hectoresen**. If rejected, revise with `/opsx:update` and present again. No behavioral code before explicit approval.
4. **IMPLEMENT**: on a feature branch using `/opsx:apply`. Follow the approved task order, relevant tests and `docs/CODE_QUALITY.md`.
5. **VERIFY**: compare every acceptance scenario with code and actual evidence; run automated checks and client tests if applicable; report tests not run.
6. **SYNC**: update canonical specs from accepted deltas; make docs and roadmap consistent.
7. **PR**: open a pull request with the change ID, approvals, checks, client compatibility status and outstanding assumptions. Do not direct-push `main`.
8. **REVIEW / ARCHIVE**: only the owner decides whether to merge. Archive after acceptance, keeping specs synchronized. **An agent must not merge or release unilaterally.**

## Exception: tiny maintenance

Typo-only, documentation-only or unambiguous mechanical maintenance can skip proposing a change; PR still required. Explain why no behavior/spec change is needed.

## Lifecycle reconciliation and documentation consistency

The owner-approved lifecycle path is limited to OpenSpec change `reconcile-openspec-lifecycle-and-status` (spec PR #13) and requires `OpenSpec-Phase: lifecycle` with the real approval metadata. It permits only specific historical task/evidence records, supported canonical capabilities and lossless archived copies of historical changes. It must **not** rewrite original proposals, delta specs, source rights or incomplete QA acceptance. See `docs/SDD_COMPLIANCE.md` and `docs/OPENSPEC_STATUS.md`.

Every agent should read `README.md` for current implemented features and explicitly execute `skills/documentation-sync/SKILL.md` before opening a functional PR. `openspec/config.yaml` describes stable architecture and links to README; do not insert a point-in-time version/status claim there. CI checks for reintroduction of the historical non-playable scaffold statement.

`add-material-profession-tooltips` for v0.1.0: itemID-based material lookup, local catalog, multiple professions independent of learned skills, enUS/esES auto language and persisted override, settings panel and no invented mappings.
