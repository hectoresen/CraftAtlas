# Proposal: Cross-agent mandatory documentation-sync skill before pull requests

## Motivation
After merged Materials/Fabricables PR #25, the maintainer found README and other documentation describing an old visual-only search, unfinished recipe explorer and obsolete test/development state. The repo also has an obsolete scaffold statement in AGENTS.md and OpenSpec config. The maintainer requests a **single portable skill**, usable by Codex, Claude Code, GitHub Copilot and other coding agents, that MUST run before opening a feature PR and that leaves functional documentation aligned with code. AGENTS.md must be **agent instructions only**, including a small table of skills and clear SDD/OpenSpec workflow, not a duplicated product manual.

## Proposed scope
- Create canonical [Agent Skills open-directory convention] skill at `.agents/skills/documentation-sync/SKILL.md` with minimal YAML frontmatter (`name`, `description`), portable Markdown workflow and no model-specific syntax dependencies. It must be directly readable when an agent lacks automatic skill discovery.
- Add lightweight discoverability shims (or exact one-line pointers with compatible frontmatter when necessary) under `.claude/skills/documentation-sync/SKILL.md` and `.github/skills/documentation-sync/SKILL.md` **only where useful and validated**; keep full procedure single-sourced under `.agents/skills/documentation-sync/SKILL.md`, not duplicated. For Codex, Claude, Copilot, OpenCode and generic tools, AGENTS.md links to the canonical file and explains explicit invocation.
- Add a **pre-PR invocation rule** in `AGENTS.md`, `CONTRIBUTING.md`, `docs/AGENT_WORKFLOW.md` and PR template. Refactor AGENTS.md to concise agent-specific instructions: read-order, project stack/DDD-style boundaries as applicable, coding/testing rules, OpenSpec two-PR approval, owner-only merge/release, skill catalog, and handoff. Remove historical feature statuses from AGENTS.md; README alone summarizes current features.
- Add `docs/DOCUMENTATION_PROTOCOL.md` as human-facing explanation and a **machine-readable documentation review manifest** (e.g. `.github/PULL_REQUEST_TEMPLATE.md` section or PR metadata), a local validation script `scripts/validate_documentation.py`, and focused `tests/test_validate_documentation.py` so the same basic checks run in CI. Feature PRs must provide truthful `Documentation-Review: updated` or `Documentation-Review: not-applicable` plus explicit justification. Do not make the gate depend on future tools or model-specific invocation.
- **Actual behavior**: read PR diff and approved spec, inspect affected user journeys + code, update README's **Current features** and limits as necessary, architecture/API/data/install/testing/roadmap/changelog as appropriate, update relevant OpenSpec implementation tasks, and record tests run/not run and current Forever build evidence. Check links/paths, generated data, stale phrases, and unsupported claims. Minimal documentation-only changes may be `not-applicable` for feature behavior but should still run review and cannot claim the README is unchanged by forgetting to inspect it.
- Correct historical `v0.0.0 scaffold` context in `openspec/config.yaml` to the actual current development reality without changing approved delta specs.
- SDD validator currently **explicitly blocks AGENTS.md in implementation PRs even if its approved scope permits it**. The governance-specific implementation must use a separately approved, **narrow allowlist for this one change** (or equivalent independent owner-approved governance phase) without allowing other implementation PRs to edit AGENTS.md. Adjust `scripts/validate_sdd.py` and `tests/test_validate_sdd.py` with strict regression tests; never weaken global owner/approval/chronology/PR scope checks.
- Extend `.github/workflows/ci.yml` to execute the docs pre-PR gate in PR context with appropriate PR body metadata and token/access limitations; retain `scripts/validate_release_checks.sh` as the existing release and data validation gate. The new docs gate must not interfere with manual release authorization.
- Apply only after owner merges this **spec-only** PR; implementation is a separate PR and can update only `tasks.md` of this approved spec.

## Skill protocol (required sections)
1. **Trigger & timing**: invoke after implementation/tests and **before composing/opening each PR** with user-facing feature changes; also on reviews/rescoping and documentation PRs as relevant. Never claim invocation if it did not run. The agent may not open the PR until it finishes or declares a blocking reason.
2. **Inputs**: base/head diff; approved OpenSpec delta, source code/tests, generated dataset details, docs and current README; screenshot/client evidence when supplied. No hallucinated files, tests, game builds or features.
3. **Agent decomposition** (optional execution parallelism): Documentation auditor (code↔README truth table); technical docs editor (architecture/data/install/development); QA/evidence reviewer (tests, coverage, real-client validation); release/history reviewer (roadmap/changelog/spec task completion); one orchestrator resolves conflicts and makes final source-of-truth decisions. Parallel workers must not write overlapping paths unless coordinator assigns ownership. This works even if the tool has only one agent (the orchestrator performs all roles serially).
4. **Mandatory updates**: README functional state, examples and limits; docs/ARCHITECTURE, DATA_MODEL, INSTALLATION, TESTING, ROADMAP, DEVELOPMENT, CHANGELOG, and touched source/API schemas only when affected; AGENTS is never feature-status documentation; ensure enUS/esES and release notes consistent.
5. **Acceptance checklist**: no planned/candidate text for merged current functionality, no fabricated "passed" tests, no incorrect named tabs or broken links, source attribution retained, exact PR scope observed, OpenSpec tasks truthful, docs reflect new behaviors as shipped. For unavailable evidence, mark `NOT RUN` and explain.
6. **Gate output**: concise Markdown documentation audit (updated/unchanged+reason for each file, tests/evidence, outstanding risks, supported git diff and actual commands), machine-readable PR attestation, open PR only after pass or explicit owner-approved exception.
7. **Non-goals**: no automatic merge, release, repository permission changes, speculative feature additions or new required external services.

## Why a separate spec is required
The proposal alters protected agent instructions, SDD governance and GitHub Actions CI; the current docs-only exemption does not authorize them. This is **not** the one-time PR #14 combined exception. The implementation must follow a merged, owner-approved spec and protect the default two-PR rules.

## Risks and mitigations
- A PR-body attestation cannot *prove* the agent internally invoked the skill. CI can require a documented review and validate affected README/docs changes; human review still verifies semantic truth. Do not claim full execution enforcement by text alone.
- A strict README-required-every-time check can create meaningless edits or block non-feature PRs. Gate only **functional change PRs**, permit narrowly justified `not-applicable`, require review of each relevant document; use stable PR metadata and tests to prevent common evasion.
- Agent-specific skill discovery conventions may evolve. Keep portable canonical Markdown and a generic AGENTS.md/manual invocation path.
- Updating governance code risks weakening SDD. Bind exception to exact approved change ID and explicit paths, test bypass attempts and preserve owner-merged approval requirements.
